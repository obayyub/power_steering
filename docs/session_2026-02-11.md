# Session Notes: Jacobian Layer-Pair Sensitivity Map (2026-02-11)

## Goal

Map Jacobian sensitivity across **all 378 layer pairs** of Qwen3-1.7B-Base (28 layers) to understand which (source, target) combinations produce the strongest steering effects, and whether logit-based metrics (singular values, KL divergence) predict generation-level behavior changes.

## Pipeline

### 1. Unified power iteration script (`power_block_iteration.py`)

Consolidated three older scripts into one clean implementation:
- Batched block power iteration (k columns along batch dim)
- Triple autograd for J^T J v computation
- Rayleigh-Ritz correction for true singular vectors
- Single/multi-prompt modes via `--num-prompts`

### 2. SVD + KL mapping (`map_jacobian.py`)

For each (source, target) pair:
1. **SVD**: 15 iterations of batched block power iteration → top-12 singular vectors + values
2. **KL divergence**: Steer with each vector (scale=10), measure KL(steered || baseline) on next-token logits

Run on 4x H100 via Lambda Cloud. Completed in ~8.5 minutes.

**Output**: `results/jacobian_map/merged.pt` — sigma_map [28,28,12], kl_map [28,28,12], all vectors

### 3. Steered generation (`map_generate.py`)

For each of 378 pairs × 12 vectors × 16 questions × 5 samples = **362,880 generations**:
- Batched per-element steering hook (all 12 vectors × 16 questions in one forward pass)
- One-shot arithmetic prompt (raw, no chat template — critical for base model)
- temp=0.7, max_new_tokens=200

Run on 4x H100. Completed in ~35 minutes.

**Output**: `results/jacobian_gen/` — per-pair JSONs, summary.json, baseline.json

## Key Findings

### Logit metrics don't predict accuracy

| Correlation | r |
|---|---|
| sigma_1 vs KL_1 | 0.24 |
| KL_1 vs accuracy | ~0 |
| sigma_1 vs accuracy | ~0 |
| Within-pair rank (sigma vs KL) | ~0 |

**sigma (linear sensitivity) and KL (distributional shift) are essentially uncorrelated with whether steering actually changes task accuracy.** A pair can have huge KL divergence (massive distributional shift) but produce no behavioral change on the arithmetic task.

### Accuracy: per-vector vs per-pair average

The pair-level accuracy (averaging across all 12 vectors) is misleading. Most vectors per pair are junk — only one or two vectors per pair matter. The real story is per-vector accuracy:

- **Baseline (unsteered): ~6%** on this arithmetic task
- **Pair-averaged accuracy**: [0.5%, 17.1%], mean=4.4% — this understates the effect
- **Best single vector per pair**: up to **90%** accuracy — 15x baseline

Top pairs by best single-vector accuracy:

| Pair | Best vec | Vec accuracy | Pair avg |
|------|----------|-------------|----------|
| (7,25) | v1 | 90.0% | 10.4% |
| (9,18) | v1 | 85.0% | 12.7% |
| (7,24) | v1 | 83.8% | 8.8% |
| (9,23) | v1 | 80.0% | 11.2% |
| (7,26) | v1 | 76.2% | 8.0% |
| (7,27) | v1 | 73.8% | 8.9% |
| (11,18) | v1 | 72.5% | 10.6% |
| (8,24) | v0 | 71.2% | 9.9% |

25 pairs have a vector exceeding 50% accuracy; 52 pairs exceed 30%.

Vector 1 (the second singular vector) is the best in 25% of all pairs. The top singular vector (v0, highest sigma) is often NOT the most behaviorally relevant — Rayleigh-Ritz ordering by singular value doesn't correspond to behavioral importance.

Example: pair (7,25) vector 1 generates genuine CoT:
```
a = 5 + 6 = 11, b = 2 + 7 = 9, a*b = 11 * 9 = 99
```

### Behavioral patterns by source layer (regex analysis)

| Source layers | Dominant behavior |
|---|---|
| 0-2 | **Broken**: repetition collapse, non-English (CJK, Cyrillic, Arabic), gibberish |
| 3-8 | Mixed: some coherent, some degenerate |
| 9-13 | **Chain-of-thought emergence**: "let me think step by step", "a = 5+6 = 11" patterns |
| 14-20 | Moderate effects, some code generation |
| 21-27 | Mild effects, closest to baseline behavior |

### Within-pair vector diversity

Different singular vectors from the same (source, target) pair produce **completely different behaviors**:
- Vector 0 might produce CoT reasoning
- Vector 1 might produce Chinese text
- Vector 2 might produce code blocks
- Vector 3 might produce repetitive tokens

This is consistent with each vector capturing a different mode of the Jacobian.

Full output in `results/jacobian_gen/behavior_analysis.txt`. Summary:

**Chain-of-thought** (X*Y=Z patterns): Source layers 9-12 dominate. (9,27) leads at 16.4%.

**Step-by-step** (a=X+Y=Z): Same region. (11,24) leads at 11.9%.

### Generalization test

Tested the two best CoT-inducing vectors on harder tasks they were never trained on. Vectors were found via power iteration on a single simple arithmetic prompt (`a=5+6, b=2+7. What is a*b?`).

**Arithmetic generalization (same format, harder problems):**

| Task | Baseline | (7,25)v1 | (9,18)v1 |
|------|----------|----------|----------|
| Level 1 — training-like (single digit) | 7.5% | 80.0% | 82.5% |
| Level 2 — big numbers (double digit adds) | 0.0% | 71.2% | 68.8% |
| Level 3 — three variables (c=a+b, what is c*2?) | 6.2% | 85.0% | 90.0% |
| Level 4 — chained ops (a=x+y, b=a*z, c=b-w) | 11.2% | 83.8% | 90.0% |

Both vectors boost accuracy from single digits to 70-90% across all difficulty levels.

**Word problems:**

| | Baseline | (7,25)v1 | (9,18)v1 |
|---|----------|----------|----------|
| Easy (25 problems) | 96.0% | 94.4% | 94.4% |
| Hard / GSM8K-style (20 problems) | 79.0% | 68.0% | 54.0% |

Easy word problems: model already solves them, steering adds noise. Hard word problems: steering actively **hurts** (79% → 54%), suggesting the vectors force a rigid arithmetic-style reasoning that interferes with the flexible reasoning needed for multi-step word problems.

**(9,18)v1 edges out (7,25)v1 on harder arithmetic (90% vs 83-85%).**

### Projection analysis: is the steering direction naturally active?

Measured the projection of the unsteered MLP down_proj activation onto the steering direction at the last token, compared to random vector projections. Also tested "bad" vectors (v0 from same pair, ~5% accuracy) and non-math control prompts.

Ratio = |steering projection| / |random projection|:

| Vector | arith_l1 | arith_l4 | word_easy | word_hard | control (non-math) |
|--------|----------|----------|-----------|-----------|---------|
| **(7,25)v1 good** | **3.68x** | **2.97x** | **2.79x** | **2.70x** | **0.60x** |
| (7,25)v0 bad | 0.34x | 0.21x | 0.35x | 0.26x | 1.33x |
| **(9,18)v1 good** | **2.18x** | **1.61x** | **1.34x** | **1.24x** | **5.37x** |
| (9,18)v0 bad | 0.20x | 1.34x | 0.71x | 0.87x | 1.74x |

Key findings:
- **Good vectors are specifically activated on math prompts.** (7,25)v1 shows 3.7x on arithmetic, 0.6x on non-math control — it's a math-specific direction.
- **Bad vectors are noise**: ~0.2-1.3x everywhere, no consistent pattern.
- **(9,18)v1 behaves differently**: 5.37x on non-math control, suggesting it's more of a general "structured reasoning" direction rather than math-specific.
- **The model's natural computation already aligns with the useful direction** — steering amplifies a latent signal that's present but insufficient on its own.

### Two vectors, two mechanisms

Per-prompt inspection of the raw signed projections revealed a clear difference:

**(7,25)v1 — math-specific direction (layer 7):**
- Arithmetic prompts: projection = +1.32 (consistently high)
- Control Q&A prompts: projection = +0.17 (noise, range 0.00 to +0.46)
- This direction is active specifically when the model processes algebraic expressions, not just any Q&A format.

**(9,18)v1 — structured response direction (layer 9):**
- Arithmetic prompts: projection = +1.02
- Control Q&A prompts: projection = +2.20 (uniformly high, range +1.69 to +2.84)
- This direction is active on **any Q&A formatted prompt** — "What is the capital of France?" gets +2.27 just like "What is the boiling point of water?" gets +2.84. It encodes something about output structure/format, not content.

The paradox: (9,18)v1 has *higher* natural activation on control than on arithmetic, yet steering with it helps arithmetic. This suggests it encodes "engage structured response mode" — something the model does naturally for trivia Q&A but fails to do for the unusual algebraic format. Forcing it on arithmetic unlocks step-by-step computation.

This also explains why (9,18)v1 degrades hard word problems more severely (79% → 54% vs 68% for (7,25)v1): it's injecting a generic structural override that conflicts with the flexible reasoning word problems require, whereas (7,25)v1's math-specific signal is more targeted.

### Probing experiments (mostly negative)

Ran three follow-up experiments (`eval_probe.py`) to test the two-mechanism hypothesis. Results were largely uninformative:

**Non-math structured tasks** (factual trivia, reasoning Q&A):

| Task | Baseline | (7,25)v1 | (9,18)v1 |
|------|----------|----------|----------|
| Factual QA (16 Qs) | 100% | 70.0% | 93.8% |
| Reasoning QA (16 Qs) | 76.2% | 67.5% | 65.0% |

Both vectors hurt non-math tasks. No evidence that (9,18)v1 usefully forces structured reasoning on non-math content — it just adds noise.

**Alternative arithmetic formats**:

| Format | Baseline | (7,25)v1 | (9,18)v1 |
|--------|----------|----------|----------|
| Original (`a=5+6, b=2+7. a*b?`) | 7.5% | 80.0% | 82.5% |
| Plain (`(5+6) * (2+7)?`) | 11.2% | 61.3% | 68.8% |
| Direct (`11 * 9?`) | 97.5% | 81.2% | 81.2% |

Key finding: the model already solves direct multiplication at 97.5%. The vectors aren't teaching arithmetic — they help parse the variable-assignment format. Both vectors actually *hurt* direct multiplication (97.5% → 81.2%).

**Scale sensitivity** (original arithmetic format):

| Scale | (7,25)v1 | (9,18)v1 |
|-------|----------|----------|
| 1 | 6% | 6% |
| 3 | 25% | 22% |
| 5 | **85%** | 57% |
| 7 | 85% | **82%** |
| 10 | 80% | 82% |
| 15 | 59% | 35% |
| 20 | 9% | 0% |

(7,25)v1 peaks earlier (scale=5) and degrades more gracefully. (9,18)v1 needs higher scale to peak and collapses faster. Both crash at scale=20.

**Combined steering** (both vectors at scale=1): 12.5% on original arithmetic — barely above baseline. The vectors don't synergize at low scale.

### Answer extraction bug fix

The original `extract_answer()` searched for the last number or last `= X` pattern in the full generated text. But the model often produces the correct answer then continues generating a new Q&A pair (mimicking the few-shot format), and the parser would pick up a stray number from the trailing text.

Fix: truncate at first `\nQ:` (model started a new question) before extracting. This is a post-processing fix — no regeneration needed for files with saved generations.

Impact on key results (rescored from saved generations):
- (7,25)v1 on arithmetic_direct: 81.2% → **100%** (steering never actually hurt direct multiplication)
- (7,25)v1 on factual_qa: 70% → **95%** (was falsely bad)
- (7,25)v1 on arithmetic_original: 80% → **92.5%**
- (9,18)v1 on word_hard: 54% → **65%** (still hurts, but less than thought)
- reasoning_qa baseline: 76% → **85%** (baseline was better than reported)

### Subtraction test (causal relevance)

Steered with negative scale (subtracting the direction) to test whether each direction is causally required for the model's natural computation. Scales: [-10, -5, -3, 0, +3, +5, +10]. Re-run with fixed extraction.

**Key results:**

| Task (baseline) | Vector | Subtract (s=-10) | Add (s=+10) |
|---|---|---|---|
| arithmetic (2.5%) | (7,25)v1 | 2% (+0%) | 92% (+90%) |
| arithmetic (2.5%) | (9,18)v1 | 1% (-1%) | 94% (+91%) |
| word_hard (77.5%) | **(7,25)v1** | **57% (-20%)** | 64% (-14%) |
| word_hard (77.5%) | (9,18)v1 | 72% (-5%) | 60% (-18%) |
| factual_qa (100%) | (7,25)v1 | 96% (-4%) | 96% (-4%) |
| factual_qa (100%) | (9,18)v1 | 100% (+0%) | 94% (-6%) |
| reasoning_qa (83.8%) | (7,25)v1 | 76% (-8%) | 72% (-11%) |
| reasoning_qa (83.8%) | (9,18)v1 | 85% (+1%) | 72% (-11%) |

Main finding:

**(7,25)v1 is causally required for word problem reasoning.** Subtracting it drops hard word problem accuracy from 77.5% to 57% (s=-10). The relationship is monotonic: s=-3 gives 65%, s=-5 gives 59%, s=-10 gives 57%. The model's natural computation at layer 7 uses this direction to solve word problems.

The earlier finding that subtracting (9,18)v1 improved reasoning QA was largely an extraction artifact. With fixed extraction, the effect shrinks to noise (+1% at s=-10, +6% at s=-3). Both vectors hurt reasoning and factual QA when added at high scale, but subtracting doesn't clearly help either.

## Bugs and Lessons

1. **Chat template on base model**: Initially used `format_chat()` (wraps in `<|im_start|>` tokens) for Qwen3-1.7B-Base. This is wrong — base models weren't trained on chat tokens. Fixed to use raw one-shot prompt.

2. **Lambda Cloud workflow**: `lambda_cloud.py run` poller can get stuck if the script finishes but `uv` process lingers. Better to launch with nohup and monitor manually.

3. **Answer extraction with few-shot prompts**: When using Q:/A: few-shot format, the model continues generating new Q&A pairs after answering. Must truncate at first `\nQ:` before extracting numbers, otherwise the parser picks up stray numbers from trailing text. This inflated error rates across multiple experiments and produced a false finding (subtraction of (9,18)v1 "improving" reasoning).
